# Changelog — kakaotalk_sender

## [0.1.6]
- **버그 수정(운영 장애)**: 클램쉘 버그(0.1.5) 수정 다음 날, 대상 3개 방 중 1개 방에
  메시지가 안 온 사고 발생. 실행 시간이 평소의 3배로 늘어난 것을 단서로 `log show`
  시스템 로그를 재구성한 결과, 방 처리 사이에 정확히 `OSASCRIPT_TIMEOUT_SECONDS`(30초)와
  일치하는 공백이 두 번 있었다 — 방 처리 후 호출되는 `close_all_room_windows()`의
  AppleScript가 응답 없이 멈췄다가 타임아웃으로 강제 종료된 것으로 보인다. 이 호출은
  실패해도 조용히 넘어가도록 설계돼 있었는데, 강제 종료 시 창 닫기 반복문이 중간에
  끊겨 일부 창이 안 닫힌 채 다음 방 처리가 시작될 수 있다는 게 문제였다 — 실제로 마지막
  방은 검색 단계 초반에 실패한 패턴(`cliclick` 호출 수가 다른 방의 절반 이하)을 보여,
  0.1.1에서 고쳤던 "이전 방 창이 다음 방 검색을 가로채는" FR-17 사고가 타임아웃이라는
  다른 경로로 재현된 것으로 판단
- `close_all_room_windows()`가 창을 닫은 뒤 실제로 메인 창만 남았는지 재확인하고, 남은
  창이 있으면 최대 2회까지 재시도하도록 강화(FR-17). 재시도로도 못 끝내면 조용히
  넘어가지 않고 명확한 에러 로그를 남김
- **로그를 파일로도 남기도록 추가(FR-19)**: 이번에도, 그리고 0.1.5 사고 때도, 이
  스킬을 best-effort로 호출하는 `ai_news_telegram`이 exit 0으로 끝나면 Hermes 크론이
  stderr를 버려 실제 에러 메시지를 볼 수 없었다 — 두 번 다 시스템 로그 정황만으로
  원인을 추정해야 했다. 종료 코드와 무관하게 항상 남는 회전 로그 파일
  (`data/kakaotalk_sender.log`, 최대 2MB × 3개)을 추가해 다음부터는 이 파일만 보면 된다
- 스모크 테스트 8개 추가

## [0.1.5]
- **버그 수정(운영 장애)**: 외부 모니터를 연결해두고 keepawake LaunchAgent도 정상 동작
  중인데도 새벽 크론 실행에서 카카오톡 발송이 계속 실패하던 문제 해결. 0.1.3에서 추가한
  FR-18(뚜껑 닫힘 조기 감지)이 `AppleClamshellState`(물리적으로 뚜껑이 닫혔는지)만 보고
  판정해, 외부 모니터+전원 연결로 macOS가 실제로는 잠들지 않는 클램쉘 모드까지 뚜껑
  닫힘으로 오판해 화면 조작을 시도하기도 전에 조기 실패시키고 있었다 — SRS 10절에는
  "외부 모니터 연결 시 예외"라고 문서화돼 있었지만 코드로 구현돼 있지 않았다
- `is_clamshell_closed()`가 같은 `ioreg` 출력에 있는 `AppleClamshellCausesSleep`(macOS
  자신이 현재 조건에서 뚜껑을 닫아도 실제로 잠들지 않는다고 판단했는지)도 함께 확인해,
  이 값이 `No`이면 뚜껑이 닫혀 있어도 실패시키지 않도록 수정. 실제 사고 시각의 시스템
  로그(`clamshelled: YES, inFullWake: YES`)로 원인 재현 확인, 스모크 테스트 2개 추가

## [0.1.4]
- **운영 환경 문제 완전 해결(코드 변경 없음, 문서화)**: 0.1.3 이후 뚜껑을 열어둬도 새벽
  실행이 계속 실패해 추가 조사한 결과, 유휴 10분 후 디스플레이 절전 → 5분 뒤 화면 잠금이
  걸리는 게 진짜 원인이었다(뚜껑 상태와 무관). `caffeinate -u -t 20`(짧게 깨움)과
  `-t 120`(넉넉히 깨움) 비교 실험으로 "디스플레이만 깨어있으면 자동화는 정상 동작"함을
  확인했고, 화면 잠금이 이미 걸린 뒤에는 실행 직전 wake로 풀 수 없다는 것도 확인했다
  (암호 자동 입력 불가)
- LOCO 프로토콜 기반 대안(node-kakao 등)을 재조사했으나 전부 죽었거나(Python 라이브러리),
  2026년 현재 카카오 서버와 호환되지 않는 상태(node-kakao, npm 배포 중단·커뮤니티 포크도
  아카이브됨)라 GUI 자동화 유지로 결론
- 해결책: 뚜껑을 닫을 경우 외부 모니터/더미 플러그 연결(클램쉘 모드), 그리고 로그인 세션
  동안 `caffeinate -d -i -s -u`를 상시 실행하는 launchd LaunchAgent로 유휴 절전/잠금 자체를
  예방 — 둘 다 이 저장소 밖의 운영 환경 설정이라 README/SRS에 필수 조건으로 문서화

## [0.1.3]
- **알려진 근본적 제약 발견 및 조기 감지 추가**: 0.1.2 이후에도 Hermes 크론 정기 실행에서
  카카오톡 발송이 계속 실패해 `/usr/bin/log show`로 실행 시각의 시스템 로그를 조사한 결과,
  그 시간 내내 맥북 뚜껑(clamshell)이 닫혀 있었음을 확인했다. 외부 모니터 없이 뚜껑이
  닫히면 디스플레이/윈도우 서버가 비활성화돼 GUI 자동화가 근본적으로 불가능하다 — 코드
  버그가 아니라 실행 시점의 물리적 조건 문제라 이 버전에서 "완전히 해결"하지는 못했다
- `ioreg`의 `AppleClamshellState`로 실행 시작 전 뚜껑 상태를 확인해(FR-18), 닫혀 있으면
  여러 단계가 각각 타임아웃되며 조용히 실패하는 대신 즉시 명확한 이유로 실패하도록 변경.
  **실제 배송이 되게 하려면 예약 실행 시각에 뚜껑을 열어두거나 외부 모니터를 연결해야
  한다**(SRS 10절, 운영상 필수 조건)
- 스모크 테스트 6개 추가

## [0.1.2]
- **버그 수정(운영 장애)**: Hermes 크론으로 정기 실행(매일 07:00)됐을 때 텔레그램 발송은
  성공했지만 카카오톡 발송이 매번 조용히 실패하던 문제의 원인을 찾아 해결. cron/launchd
  같은 비대화형 환경은 PATH에 Homebrew 경로(`/opt/homebrew/bin`)가 없어
  `shutil.which("cliclick")`이 항상 실패했다 — 대화형 터미널 테스트에서는 매번
  `eval "$(brew shellenv)")`를 직접 실행해왔기 때문에 지금까지 드러나지 않았다
- `resolve_cliclick_path()`를 추가해 `shutil.which` 실패 시 Homebrew의 일반 설치 위치
  (`/opt/homebrew/bin/cliclick`, `/usr/local/bin/cliclick`)도 확인하고, 이후 `cliclick`
  호출도 이 절대 경로를 사용하도록 변경 — 호출 환경의 PATH 설정에 더 이상 의존하지 않음
- 실제 크론 실행 환경의 PATH를 그대로 재현해 문제 재현 및 해결 확인, 스모크 테스트 4개 추가

## [0.1.1]
- `ai_news_telegram` 연동 첫 실사용 중, 여러 방을 순차 처리할 때 이전 방의 대화창을
  닫지 않아 다음 방 검색어가 그 창의 메시지 입력창에 잘못 입력되는 사고 확인 후 수정 —
  방 처리 후(성공/실패 무관) 메인 목록 창만 남기고 나머지 창을 닫도록 변경(FR-17).
  같은 방을 연속 두 번 처리하는 회귀 테스트로 실제 환경 재검증 완료
- 전송 검증(FR-12) 타임아웃을 `OSASCRIPT_TIMEOUT_SECONDS`(15→30초)/
  `SEND_VERIFY_TIMEOUT_SECONDS`(5→35초)로 상향
- **알려진 문제(미해결)**: 위 타임아웃 상향에도 불구하고, 실제 리포트 수준(약 1,800자)
  메시지 3건을 실제 대화방 3곳에 보낸 결과 **전송 자체는 매번 성공**했지만 전송 검증
  단계는 매번 타임아웃으로 실패 보고됨을 확인했다. 즉 이 버전은 긴 메시지에서
  `kakaotalk_sender`가 "실패"를 보고해도 실제로는 도착했을 가능성이 높다 — 로그만으로
  성공 여부를 신뢰할 수 없다. 근본 원인 조사 및 검증 로직 재설계는 다음 패치 과제로
  SRS 10절에 기록
- 스모크 테스트 2개 추가

## [0.1.0]
- macOS에 설치되어 로그인된 카카오톡 데스크톱 앱을 `cliclick`(실제 클릭/키 이벤트) +
  System Events(AppleScript)로 조작해 지정 대화방(들)에 텍스트 메시지를 전송하는 기능 구현
- 검색으로 대화방을 정확히 일치하는 이름으로 찾고, 더블클릭으로 연 뒤 열린 창 이름을
  재확인해 다른 대화방이 잘못 열리는 오동작을 방지
- 메시지는 클립보드(UTF-8 인코딩 명시)로 설정 후 붙여넣고, 붙여넣은 내용을 클립보드
  왕복으로 재확인한 뒤에만 전송 버튼을 클릭
- 전송 후 대화 내역에서 보낸 텍스트를 직접 읽어 전송 검증(입력창이 비워졌는지 여부는
  신뢰할 수 없어 판단 근거로 쓰지 않음)
- 여러 `--room`을 순차 처리하고 방별 성공/실패를 집계, 하나라도 실패하면 0이 아닌
  종료 코드 반환
- 마우스 클릭/키 입력 직전마다 시스템 frontmost 프로세스가 KakaoTalk인지 확인하는
  안전장치 적용 — 실제 검증 중 다른 앱으로 키 입력이 새는 오동작이 재현되어 필수로 채택
- 앱 미설치/Accessibility 권한 거부/로그인 안 됨(타임아웃)을 구분되는 예외로 분류해
  명확한 안내 메시지 제공(화면 잠금 상태는 미검증)
- 실제 카카오톡 계정·대화방으로 정상 케이스/존재하지 않는 방/부분 실패 케이스 end-to-end
  검증 완료
- 스모크 테스트 18개 추가(`tests/test_main.py`), macOS UI 자동화 호출은 전부 mock 처리
