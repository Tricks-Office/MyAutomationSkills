# Implementation Plan: kakaotalk_sender

- 작성일: 2026-08-10
- 작성자: devjan
- 상태: 초안
- 관련 SRS: [`SRS.md`](./SRS.md) — 이 문서는 SRS를 대체하지 않는다. SRS는 "무엇을/왜"
  만드는지, 이 문서는 "어떤 순서로" 만드는지를 다룬다.

## 1. 단계로 나누는 이유
- 이 스킬의 핵심 동작 방식(macOS System Events로 카카오톡 Mac 앱을 조작)은 실제로
  검증된 적이 없다. 채팅방 목록/검색창/입력창을 접근성 트리에서 어떻게 식별하는지,
  클립보드 붙여넣기가 정상 동작하는지, 전송한 메시지를 다시 읽어 검증할 수 있는지가
  모두 SRS 작성 시점에는 불확실하다(SRS 8절, 10절) — 구현 전 실사 확인이 필요한 불확실한
  외부 스펙이 있다는 `CLAUDE.md` 3.1.1 기준에 해당한다.
- 전송 검증 방식(SRS FR-6)이 스파이크 결과에 따라 바뀔 수 있어, 검증 로직에 의존하는
  이후 단계(다중 방 처리, 예외 처리)를 스파이크보다 먼저 구현할 수 없다.

## 3. Phase별 상세

### Phase 0: 뼈대 + UI 자동화 스펙 확인
- 범위:
  - `skills/kakaotalk_sender/`에 `src/`, `tests/`, `requirements.txt` 골격 생성
  - 실제 macOS 환경에서 `osascript`로 KakaoTalk.app을 `activate`하고, System Events로
    접근성 트리를 탐색해 다음을 확인한다:
    - 채팅방 목록/검색 필드/개별 채팅방 항목을 식별하는 방법(요소 타입, 이름/역할 속성)
    - 대화방을 열었을 때 메시지 입력창을 식별하는 방법
    - 클립보드에 텍스트를 설정한 뒤 Cmd+V로 입력창에 삽입이 되는지, 멀티라인 텍스트의
      줄바꿈이 유지되는지
    - 전송(Return) 직후 마지막 채팅 버블이 접근성 트리에 텍스트로 노출되는지(노출되면
      FR-6의 "정확 일치 검증"을 그대로 채택, 노출되지 않으면 SRS 10절에 명시한 대로
      "입력창이 비워졌는지" 등 약한 검증으로 FR-6을 수정)
    - 대략적으로 붙여넣기 가능한 메시지 길이 상한(공식 스펙이 없으므로 실측)
  - 확인 결과를 SRS 6절(흐름)/FR-6/8절/10절에 반영(필요 시 FR-6 문구 수정)
  - CLI 골격 작성: `argparse`로 `--room`(반복), `--message`/`--message-file`(상호배타)
    파싱 및 유효성 검증(FR-1), macOS 여부 확인(FR-2)
  - 앱 활성화 함수 작성(FR-3 스파이크 수준 — 메인 창 존재 확인까지만, 로그인 안 됨/권한
    거부 등 세부 예외 분기는 Phase 2로 미룸)
  - 하드코딩된 단일 방 이름 + 하드코딩 메시지로, 위에서 확인한 방식을 그대로 사용해 실제
    카카오톡 메시지 1건을 전송해 수동으로 도착을 확인(검증 로직 자동화는 이 Phase에서
    제외)
- 이번 Phase에서 제외하는 것(다음 Phase로 미룸): 여러 방 처리, 방 검색의 중복/미존재
  처리, 전송 검증 로직의 자동화, SRS 7절 예외 처리 전체
- 완료 기준(Definition of Done): 하드코딩된 방 이름 하나로 `python src/main.py`를 실행하면
  실제 카카오톡 메시지 1건이 정상 도착(수동 확인). UI 요소 식별 방법/붙여넣기 결과/전송
  검증 가능 여부가 SRS에 반영됨
- 커밋 단위:
  1. `kakaotalk_sender: 기본 골격(src/tests/requirements.txt) 구성`
  2. `kakaotalk_sender: AppleScript/System Events UI 자동화 스펙 확인 결과 SRS 반영`
  3. `kakaotalk_sender: 하드코딩 단일 방 전송 end-to-end 확인`

### Phase 1: 방 검색 + 전송 + 검증
- 범위:
  - 대화방 검색 함수: 이름 정확 일치로 검색, 결과 0개/2개 이상이면 실패로 반환(FR-4)
  - 클립보드 설정 → 붙여넣기 → Return 전송 함수(FR-5)
  - Phase 0에서 확정한 방식으로 전송 검증 함수 구현, 실패/타임아웃 시 실패로 반환(FR-6)
  - 위 세 함수를 하나로 묶어 "단일 방에 메시지 보내고 결과(성공/실패, 실패 사유) 반환"
    하는 함수 완성
- 이번 Phase에서 제외하는 것: 여러 방 순회, 앱 레벨 예외(로그인 안 됨/권한 거부/화면
  잠금), 결과 집계/종료 코드
- 완료 기준(Definition of Done): 단일 `--room` 인자로 정상 케이스, 존재하지 않는 방,
  중복 이름 방, 전송 검증 실패 케이스가 각각 SRS 7절대로 동작(정상 케이스는 실제 환경
  수동 확인, 나머지는 가능한 범위에서 재현)
- 커밋 단위:
  1. `kakaotalk_sender: 대화방 검색(정확 일치/중복·미존재 처리) 구현`
  2. `kakaotalk_sender: 클립보드 붙여넣기 전송 + 전송 검증 구현`

## 5. Phase 간 의존성
- 전체적으로 순차 진행이다: Phase 1은 Phase 0에서 확정한 UI 요소 식별 방법과 전송
  검증 방식에 그대로 의존하므로 Phase 0 완료 없이는 시작할 수 없다. Phase 2는 Phase 1의
  "단일 방 처리" 함수를 순회하며 감싸는 구조라 Phase 1 완료가 선행돼야 한다. Phase 3의
  mock 테스트는 Phase 0~2에서 함수 단위로 분리된 로직이 있어야 작성 가능해 마지막에
  진행한다.
- Phase 0 내부에서 "UI 자동화 스펙 확인"과 "CLI 인자 파싱 골격"은 서로 독립적이라 순서를
  바꿔도 무방하지만, 스펙 확인 결과가 이후 모든 Phase의 전제가 되므로 스펙 확인을 먼저
  마치는 편을 권장한다.

## 6. 중단 시 상태
- Phase 0까지만 완료 후 중단: 하드코딩된 단일 방에 수동 확인용 전송만 가능한 상태.
  실사용 불가. 다른 스킬 폴더를 참조하지 않으므로 다른 스킬에는 영향 없음(스킬 격리
  원칙, `CLAUDE.md` 3.3).
- Phase 1까지만 완료 후 중단: 단일 `--room`을 CLI로 지정해 정상 전송이 가능하지만, 여러
  방 처리와 앱 레벨 예외 처리(로그인 안 됨, 권한 거부 등)가 없어 제한적으로만 실사용
  가능.
- Phase 2까지 완료: SRS 기능 요구사항 전체 충족, 실사용 가능하나 자동 테스트/문서가 없어
  Hermes 등록 전 단계.
- Phase 3까지 완료: SRS 요구사항 전체 충족, Hermes 등록 준비 완료.
- 각 Phase는 다른 스킬 폴더를 참조하지 않으므로, 어느 시점에 중단되어도 기존 스킬(
  `ai_news_telegram` 등)의 동작에는 영향을 주지 않는다.
