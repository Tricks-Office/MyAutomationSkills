- 작성일: 2026-08-10 (Phase 0 완료 반영: 2026-08-11)
- 작성자: devjan
- 상태: 진행중 (Phase 0 완료)
- 관련 SRS: [`SRS.md`](./SRS.md) — 이 문서는 SRS를 대체하지 않는다. SRS는 "무엇을/왜"
  만드는지, 이 문서는 "어떤 순서로" 만드는지를 다룬다.

## 1. 단계로 나누는 이유
- 이 스킬의 핵심 동작 방식(macOS UI 자동화로 카카오톡 Mac 앱을 조작)은 실제로 검증된 적이
  없었다. 채팅방 목록/검색창/입력창을 접근성 트리에서 어떻게 식별하는지, 클립보드
  붙여넣기가 정상 동작하는지, 전송한 메시지를 다시 읽어 검증할 수 있는지가 모두 SRS
  작성 시점에는 불확실했다 — 구현 전 실사 확인이 필요한 불확실한 외부 스펙이 있다는
  `CLAUDE.md` 3.1.1 기준에 해당한다.
- **Phase 0 스파이크 결과, 실제로 당초 예상과 다른 근본적인 사실이 드러났다**: 접근성
  API 기반의 합성 클릭/키 입력(System Events)만으로는 이 앱을 안정적으로 자동화할 수
  없고, `cliclick`(외부 도구)로 실제 HID 이벤트에 가까운 합성 이벤트를 보내야만 방을
  열고 메시지를 붙여넣고 전송하는 동작이 실제로 동작한다. 이는 SRS 8절/10절에 반영했다.
- 전송 검증 방식(SRS FR-12)이 스파이크 결과에 따라 바뀔 수 있어, 검증 로직에 의존하는
  이후 단계(다중 방 처리, 예외 처리)를 스파이크보다 먼저 구현할 수 없었다 — 실제로는
  당초 우려했던 "약한 검증으로 대체" 시나리오 없이, 원래 설계대로의 강한 검증(정확 일치)이
  가능함이 확인됐다.

## 3. Phase별 상세

### Phase 0: 뼈대 + UI 자동화 스펙 확인 — **완료 (2026-08-11)**
- 범위 및 실제 진행 경과:
  - 실제 macOS 환경에서 `osascript`/System Events로 KakaoTalk.app을 조작하며 UI 요소
    구조를 확인함. 채팅방 목록/검색 결과는 `AXTable`의 row로 접근 가능하고, 각 row의
    `AXCell` 하위 `AXStaticText`로 방 이름을 정확히 매칭할 수 있음을 확인.
  - **핵심 블로커 발견**: System Events의 `click`/`perform action "AXPress"`로는 방을
    열 수 없었다(더블클릭 시뮬레이션이 clickCount=2로 전달되지 않는 것으로 추정). 메뉴바,
    컨텍스트 메뉴(AXShowMenu), Return 키 등 대안도 모두 실패.
  - Homebrew가 설치되어 있지 않아 먼저 설치(사용자가 직접 터미널에서 진행, 관리자
    비밀번호 필요해 에이전트가 대신 실행 불가)한 뒤 `brew install cliclick` 진행.
  - `cliclick`의 더블클릭(`dc:x,y`)으로 방 열기 성공. 이후 검색창 포커스, 메시지 입력창
    포커스도 접근성 API 클릭만으로는 불안정해 `cliclick` 단일 클릭이 필요함을 확인.
  - **실제 오동작 2건 재현**: (1) 오래된 좌표로 더블클릭한 결과 의도한 테스트방이 아닌
    실제 다른 대화방이 열림 → 즉시 창 닫고 복구. (2) frontmost 확인 없이 진행하다 키
    입력이 KakaoTalk이 아닌 VS Code로 유입됨 → 사용자가 직접 확인해 무해함을 확인. 이
    두 사례를 계기로 "frontmost 안전장치"와 "방 열기 후 이름 재확인"을 SRS에 필수
    요구사항(FR-5, FR-7)으로 추가함.
  - 클립보드 붙여넣기: 셸에서 로케일 미설정 시 `pbcopy`가 한글을 깨뜨림을 발견 → Python
    `subprocess`에서 UTF-8 인코딩 명시로 해결. System Events의 `keystroke ... using
    {command down}` 기반 Cmd+V는 포커스가 확인된 상태에서도 간헐적으로 무시됨을 반복
    재현 → `cliclick`의 `kd:cmd t:v ku:cmd` 조합으로 대체해 안정적으로 성공.
  - 입력창 접근성 `value`가 신뢰할 수 없음을 발견(내용이 있어도 빈 값 보고) → 전체선택
    +복사 후 클립보드 재확인 방식을 붙여넣기 검증 수단으로 채택.
  - 전송: `AXPress`/`Return` 키 모두 입력창을 비우지만 실제 전송은 안 됨을 여러 차례
    재현(사용자가 실제 화면에서 "메시지가 안 보인다"고 반복 확인해줌). `cliclick`으로
    전송 버튼을 클릭(마우스 이동 후 클릭)해서야 실제 전송 성공.
  - 전송 검증: 대화 내역 `AXTable`의 row에서 상대방 메시지, 내가 보낸 메시지 모두 원문
    텍스트를 읽을 수 있음을 확인 — 멀티라인 메시지(3줄)도 줄바꿈이 유지된 채 전송·검증
    성공, 사용자가 실제 화면으로 최종 확인함.
  - 확인 결과를 SRS 3절(FR 전면 재정의)/6절(흐름)/8절(외부 의존성)/10절(제약사항)에 반영함.
- 이번 Phase에서 제외한 것(다음 Phase로 미룸): 여러 방 처리, 방 검색의 중복 처리 코드화,
  화면 잠금/Accessibility 권한 거부 케이스의 정확한 에러 형태 확인, `src/` 코드 골격
  자체는 아직 작성하지 않음(스파이크는 대화형으로 셸 명령을 직접 실행하며 진행함)
- 완료 기준(Definition of Done): 하드코딩된 방 이름("ChatBotTest")으로 실제 카카오톡
  메시지가 전송되고, 접근성 트리 읽기로 전송 검증까지 성공 — **달성**. UI 요소 식별
  방법/붙여넣기 결과/전송 검증 가능 여부가 SRS에 반영됨 — **달성**.
- 이번 Phase는 대화형으로 셸 명령을 직접 실행하며 진행해 `CLAUDE.md` 3.2 기준의 "커밋
  단위"로 나누지 않았다. 코드 골격은 Phase 1에서 파일로 작성하며 그때부터 커밋을 나눈다.

### Phase 1: Phase 0 방식을 코드로 정리(단일 방) — **완료 (2026-08-11)**
- 범위 및 실제 진행 경과:
  - `skills/kakaotalk_sender/`에 `src/`, `tests/`, `requirements.txt` 골격 생성
  - Phase 0에서 확정한 방식을 함수 단위로 옮김: `cliclick` 존재 확인(FR-3), 앱 활성화
    (FR-4 중 activate 부분), 방 검색(FR-6), 방 열기+이름 재확인(FR-7), 클립보드 설정
    (FR-8), 붙여넣기(FR-9), 붙여넣기 확인(FR-10), 전송(FR-11), 전송 검증(FR-12)
  - CLI 골격 작성: `argparse`로 `--room`(반복), `--message`/`--message-file`(상호배타)
    파싱 및 유효성 검증(FR-1), macOS 여부 확인(FR-2)
  - **실제 환경 재검증에서 새로 발견한 문제 2건과 해결**(당초 Phase 0에서는 드러나지
    않았던 문제로, 코드화·재실행 과정에서만 재현됨):
    1. `Cmd+F`로 검색을 여는 방식이 **토글**로 동작해, 이미 검색이 열려 있는 상태(예:
       이전 실행의 잔여 상태)에서 다시 호출하면 오히려 닫혀버림 → 검색창이 이미 열려
       있는지 먼저 확인하고 없을 때만 "검색" 버튼(이 버튼도 동일하게 토글)을 클릭하는
       방식으로 멱등화.
    2. 검색어 입력에 System Events `keystroke`로 "전체선택(Cmd+A) 후 타이핑"을
       시도했으나 select-all이 간헐적으로 실패해, 여러 방을 순회할 때 이전 검색어에
       새 검색어가 이어붙거나 한글 자모가 깨진 문자열이 검색창에 남는 문제가 실제로
       재현됨 → 메시지 입력창과 동일하게 클립보드 설정 + cliclick 기반 Cmd+A/Cmd+V로
       대체해 해결.
  - **frontmost 안전장치(FR-5)와 여러 방 순차 처리·결과 집계(FR-13, FR-14, FR-15)는
    당초 계획(Phase 2로 예정)보다 앞당겨 Phase 1에서 함께 구현했다** — 실제 환경에서
    반복 테스트하는 과정 자체가 frontmost 오동작 위험에 노출되어 있어, 핵심 로직을
    작성하는 시점부터 안전장치를 넣는 것이 더 안전하다고 판단했기 때문이다. 이에 따라
    Phase 2의 범위는 앱 레벨 예외의 세부 분류(로그인 안 됨/권한 거부/화면 잠금 감지)로
    좁아졌다(아래 Phase 2 참고).
  - 실제 환경에서 end-to-end 테스트 완료: 정상 케이스(성공), 존재하지 않는 방(실패),
    부분 실패(유효한 방 1개 + 존재하지 않는 방 1개 동시 처리) 모두 사용자가 실제
    카카오톡 화면으로 확인
  - 확인 결과를 SRS FR-6/8절/10절에 반영함
- 완료 기준(Definition of Done): 단일 `--room` 인자로 정상 케이스가 실제 환경에서
  성공 — **달성**. 존재하지 않는 방/부분 실패 케이스가 SRS 7절대로 동작 — **달성**.
  (붙여넣기 확인 실패/전송 검증 실패의 인위적 재현은 하지 않음 — 정상 동작 확인으로
  충분하다고 판단, 필요 시 Phase 3 테스트 단계에서 mock으로 보완)
- 커밋 단위:
  1. `kakaotalk_sender: 기본 골격(src/tests/requirements.txt) 구성 + 핵심 로직 구현`
  2. `kakaotalk_sender: 실제 환경 검증 중 발견한 검색 토글/한글 입력 문제 수정`
  3. `kakaotalk_sender: 스모크 테스트 추가`

## 5. Phase 간 의존성
- 전체적으로 순차 진행이다: Phase 1은 Phase 0에서 확정한 UI 요소 식별 방법과 상호작용
  방식(cliclick 기반)에 그대로 의존하므로 Phase 0 완료 없이는 시작할 수 없었다(완료됨).
  Phase 2(앱 레벨 예외 세분화)는 Phase 1의 앱 활성화 함수를 보강하는 구조라 Phase 1
  완료가 선행돼야 한다. Phase 3의 문서화는 코드가 안정된 뒤 진행하는 것이 자연스러워
  마지막에 진행한다.
- (변경 이력) 당초 계획에서는 frontmost 안전장치와 다중 방 처리를 Phase 2로 미뤘으나,
  Phase 1을 실제 환경에서 반복 검증하는 과정 자체가 오동작 위험에 노출되어 있어 Phase 1
  단계에서 함께 구현했다(3절 Phase 1 참고). 이에 따라 Phase 2는 앱 레벨 예외 세분화만
  남은 좁은 범위가 됐다.

## 6. 중단 시 상태
- Phase 0까지만 완료 후 중단: 코드 골격이 아직 없고, 대화형으로 확인한 방식과 결과만
  SRS/Implementation Plan에 문서화되어 있다. 실사용 불가. 다른 스킬 폴더를 참조하지
  않으므로 다른 스킬에는 영향 없음(스킬 격리 원칙, `CLAUDE.md` 3.3).
- Phase 1까지만 완료 후 중단(현재 상태): frontmost 안전장치, 여러 방 순차 처리, 결과
  집계/종료 코드까지 포함되어 있어 SRS 기능 요구사항 대부분을 충족한 상태로 실사용
  가능하다. 다만 앱 레벨 예외(로그인 안 됨/권한 거부/화면 잠금)의 에러 메시지가
  세분화되어 있지 않아 원인 파악이 어려울 수 있다(범용 예외 메시지로만 표시됨).
- Phase 2까지 완료: SRS 기능 요구사항 전체 충족, 안전장치 포함 실사용 가능하나 자동
  테스트/문서가 없어 Hermes 등록 전 단계.
- Phase 3까지 완료: SRS 요구사항 전체 충족, Hermes 등록 준비 완료.
- 각 Phase는 다른 스킬 폴더를 참조하지 않으므로, 어느 시점에 중단되어도 기존 스킬(
  `ai_news_telegram` 등)의 동작에는 영향을 주지 않는다.
