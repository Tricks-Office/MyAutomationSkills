## 1. 개요
이 컴퓨터(macOS)에 설치되어 이미 로그인되어 있는 카카오톡 데스크톱 앱을 조작해 지정한
대화방(들)에 텍스트 메시지를 전송하는 범용 스킬이다. 카카오톡 계정의 별도 인증이나 세션
토큰 추출, 비공식 API/프로토콜 연동을 전혀 사용하지 않고, 이미 로그인된 앱 화면을 사람이
클릭·타이핑하는 것과 동일한 방식으로 조작한다(설계 배경은 8절 참고).

**Phase 0 스파이크(2절 용어, 4절 참고)에서 확인된 핵심 사실**: 이 앱의 채팅방 목록/검색
결과 행, 전송 버튼 등 커스텀 렌더링된 UI 요소는 macOS 접근성 API의 합성 이벤트(System
Events의 `click`, `perform action "AXPress"`, `keystroke`)에 안정적으로 반응하지 않는다.
실제 마우스/키보드 하드웨어 이벤트에 가까운 합성 이벤트를 만들어주는 외부 도구
(`cliclick`)가 있어야 방을 열고 메시지를 붙여넣고 전송하는 동작이 실제로 동작한다. 이는
당초 8절에 적었던 "표준 라이브러리만으로 충분할 것" 가정을 뒤집는 결과이며, 이 SRS
전반에 반영했다.

이 스킬은 특정 리포트(예: `ai_news_telegram`)에 종속되지 않는 범용 "카카오톡 발송기"로
설계한다. 다른 스킬은 이 스킬의 코드를 import하지 않고, `CLAUDE.md` 3.3의 스킬 격리
원칙에 따라 `python skills/kakaotalk_sender/src/main.py ...`를 서브프로세스로 호출해
재사용한다.

## 2. 용어 정의
| 용어 | 정의 |
|---|---|
| 대상 대화방 | `--room` 인자로 지정한, 메시지를 받을 카카오톡 채팅방 이름(정확히 일치해야 함) |
| 전송 검증 | 메시지 전송 직후, 대화 내역 테이블의 최근 행들을 접근성 트리에서 읽어 보낸 텍스트가 실제로 나타나는지 정확 일치로 확인하는 절차. Phase 0에서 실현 가능함이 확인됨(FR-9) |
| 완전 실패 | 앱 활성화/로그인 확인/frontmost 확인 단계에서 실패해 어떤 방에도 전송을 시도조차 못한 상태 |
| 부분 실패 | 하나 이상의 방은 전송에 성공했지만, 다른 하나 이상의 방은 실패한 상태 (완전 실패와 구분) |
| frontmost 안전장치 | 마우스 클릭이나 키 입력을 보내기 직전, macOS 시스템 전체에서 실제로 최상단(활성) 프로세스가 "KakaoTalk"인지 확인하는 절차. Phase 0에서 이 확인 없이 진행하다 다른 앱(VS Code)으로 키 입력이 샌 사례가 실제로 발생해 모든 상호작용 직전 필수 절차로 채택함 |
| 실클릭(real click) | `cliclick` 등 OS 레벨 HID 이벤트에 가까운 합성 이벤트로 발생시키는 클릭/키 입력. System Events의 `click`/`keystroke`(accessibility API 기반, "가짜 클릭"이라 부름)와 대비되는 개념 |

## 3. 기능 요구사항
| ID | 요구사항 설명 | 우선순위(필수/선택) |
|---|---|---|
| FR-1 | CLI 인자로 `--room`(반복 가능, 1개 이상 필수)과 `--message`(문자열) 또는 `--message-file`(파일 경로) 중 정확히 하나를 받는다. `--room`이 없거나, `--message`/`--message-file`이 둘 다 없거나 둘 다 있으면 실행 시작 전 실패 처리한다 | 필수 |
| FR-2 | 실행 시작 시 `sys.platform`이 macOS(`darwin`)가 아니면 즉시 실패 처리한다 | 필수 |
| FR-3 | `cliclick`의 실행 파일 경로를 찾아(`shutil.which`, 실패 시 Homebrew의 일반 설치 위치인 `/opt/homebrew/bin/cliclick`, `/usr/local/bin/cliclick`도 확인) 실행 시작 전 확인하고, 이후 `cliclick` 호출에도 이 절대 경로를 사용한다. 어디서도 못 찾으면 설치 방법 안내와 함께 실패 처리한다 — cron/launchd 등 비대화형 환경은 PATH에 Homebrew 경로가 없어 `shutil.which`만으로는 찾지 못하는 사고가 실제로 있었다(8절) | 필수 |
| FR-4 | KakaoTalk.app을 활성화(activate)한 뒤, 지정 타임아웃(기본 10초) 내에 메인 창(채팅방 목록)이 접근성 트리에 나타나는지 확인한다. 나타나지 않으면(앱 미설치/로그인 안 됨/응답 없음) 완전 실패로 처리한다 | 필수 |
| FR-5 | **frontmost 안전장치(2절)**: 마우스 클릭 또는 키 입력을 보내기 직전마다, macOS 시스템 전체의 frontmost 프로세스 이름이 정확히 "KakaoTalk"인지 확인한다. 아니면 그 즉시(재시도 없이) 실패로 처리한다 — 이 확인은 방 검색·방 열기·붙여넣기·전송 등 상호작용이 있는 모든 단계 직전에 반복 수행한다 | 필수 |
| FR-6 | `--room`으로 지정된 각 대화방에 대해 순차적으로(동시 실행 없이) 처리한다: 검색창(AXTextField)이 이미 열려 있는지 먼저 확인하고, 없으면 "검색" 버튼을 실클릭으로 눌러 연다 — `Cmd+F`와 "검색" 버튼 모두 이미 열려 있는 상태에서 다시 실행하면 오히려 닫히는 **토글**로 동작함이 Phase 1에서 확인되어, 먼저 상태를 확인한 뒤 필요할 때만 클릭한다. 검색창을 실클릭으로 포커스한 뒤, 방 이름을 클립보드에 설정하고 cliclick으로 전체선택(`kd:cmd t:a ku:cmd`)+붙여넣기(`kd:cmd t:v ku:cmd`)해 입력한다 — 당초 System Events `keystroke`로 "전체선택 후 타이핑"을 시도했으나 select-all이 간헐적으로 실패해 이전 검색어에 새 검색어가 이어붙거나 일부 한글 자모가 깨지는 문제가 Phase 1 실제 검증에서 재현되어 채택하지 않는다. 검색 결과에서 이름이 정확히 일치하는 행을 찾아, 결과가 0개이거나 2개 이상이면 그 방은 실패로 기록하고 다음 방으로 진행한다(다른 방을 임의로 추측해 열지 않는다) | 필수 |
| FR-7 | 검색 결과에서 찾은 행은 **cliclick의 더블클릭(`dc:x,y`)**으로 연다 — System Events의 `click`/`perform action "AXPress"`로는 이 앱의 방이 열리지 않음이 Phase 0에서 확인됨. 방을 연 뒤, 새로 열린 창의 이름이 대상 방 이름과 정확히 일치하는지 재확인한다. 불일치하면 즉시 그 방을 실패로 기록하고(다른 실제 대화방이 열렸을 수 있으므로 계속 진행하지 않음) 다음 방으로 진행한다 | 필수 |
| FR-8 | 메시지 텍스트는 Python에서 명시적으로 UTF-8로 인코딩해 클립보드에 설정한다(`subprocess.run(["pbcopy"], input=text.encode("utf-8"))`) — 로케일(LANG/LC_ALL) 설정 없이 셸에서 직접 `pbcopy`를 호출하면 한글 텍스트가 깨질 수 있음이 확인됨(8절) | 필수 |
| FR-9 | 메시지 입력창을 **실클릭**으로 포커스한 뒤, **cliclick의 키 이벤트 조합(`kd:cmd t:v ku:cmd`)**으로 붙여넣는다 — System Events의 `keystroke "v" using {command down}`은 이 앱에서 간헐적으로 무시됨(포커스는 정상으로 확인되는데도 붙여넣기가 씹히는 사례가 반복 재현됨)이 Phase 0에서 확인되어 채택하지 않는다 | 필수 |
| FR-10 | 붙여넣기 직후, 전체 선택(`Cmd+A`)과 복사(`Cmd+C`)를 실행해 시스템 클립보드를 다시 읽고 원본 메시지와 정확히 일치하는지 확인한다. 일치하지 않으면 전송을 시도하지 않고 그 방을 실패로 기록한다 — 입력창의 접근성 `value` 속성은 실제 내용이 있어도 빈 값으로 보고되는 등 신뢰할 수 없음이 확인되어, 이 방식(클립보드 왕복 확인)을 채택한다 | 필수 |
| FR-11 | 붙여넣기 확인(FR-10)에 성공하면, "전송" 버튼을 **cliclick으로 클릭**(마우스를 버튼 위치로 이동한 뒤 클릭)해 전송한다 — `Return` 키(System Events) 및 `AXPress` 액션은 입력창을 비우기는 하지만 실제 전송을 안정적으로 트리거하지 못함(입력창만 비워지고 메시지가 도착하지 않는 오탐이 Phase 0에서 여러 차례 재현됨)이 확인되어 채택하지 않는다 | 필수 |
| FR-12 | 전송 후, 대화 내역 테이블의 최근 행들을 순회해 보낸 메시지 텍스트가 실제로 나타나는지 확인한다(전송 검증, 2절). 지정 타임아웃(기본 35초) 내에 나타나지 않으면 그 방은 실패로 기록한다. **입력창이 비워졌는지 여부는 전송 성공의 근거로 사용하지 않는다** — 위 FR-11의 이유와 동일하게 신뢰할 수 없는 신호이기 때문이다. **알려진 한계**: 약 1,800자 이상의 긴 메시지에서는 35초로 늘린 뒤에도 이 검증 단계가 타임아웃되는 사례가 재현됐고, 카카오톡이 대화 내역의 접근성 값 자체를 일부 길이 이상에서 말줄임(…)으로 잘라 노출하는 것으로 보여 정확 일치 비교가 성립하지 않을 수도 있다 — 두 경우 모두 **실제 전송 자체는 성공했는데 검증만 실패로 오탐**되는 것으로 실사용에서 확인됐다(8절, 10절) | 필수 |
| FR-13 | 방 단위 처리는 자동 재시도하지 않는다(1회 시도, 성공/실패만 기록) — 자동 재시도가 오히려 중복 전송 위험을 키운다고 판단했기 때문. 재시도가 필요하면 호출자가 실패한 방만 골라 다시 실행한다 | 필수 |
| FR-17 | 방 하나의 처리가 끝나면(성공/실패 무관) 메인 목록 창("카카오톡")을 제외한 모든 창을 닫는다. 이전 방의 대화창이 열려 있는 채로 다음 방을 검색하면, 화면 좌표 클릭이 메인 목록 창이 아니라 열려 있는 이전 대화창을 대신 맞혀 다음 방 검색어가 그 창의 메시지 입력창에 잘못 입력되는 사고가 실제로 재현됐다(8절). 창을 닫은 뒤에는 실제로 메인 목록 창만 남았는지 조회로 재확인하고, 남은 창이 있으면 최대 `CLOSE_WINDOWS_MAX_ATTEMPTS`(2)회까지 재시도한다 — 창 닫기 AppleScript 호출 자체가 타임아웃으로 강제 종료되면 반복문이 중간에 끊겨 일부 창이 남을 수 있음이 2026-08-17 실사용에서 확인됐다(8절). 재시도로도 못 끝내면 조용히 다음 방으로 넘어가지 않고 명확한 에러 로그를 남긴다 | 필수 |
| FR-18 | 실행 시작 전 `ioreg`로 맥북 뚜껑(clamshell)이 닫혀 있는지, 그리고 닫혀 있다면 `AppleClamshellCausesSleep` 값으로 외부 모니터+전원 연결 등으로 macOS가 실제로는 잠들지 않는다고 판단한 클램쉘 모드인지까지 함께 확인한다(2026-08-16, 10절 참고). 뚜껑이 닫혀 있고 이 클램쉘 모드 예외에도 해당하지 않을 때만 즉시 명확한 이유로 실패 처리한다. 관련 속성이 없는 환경(데스크톱 Mac 등)에서는 판단하지 않고 그대로 진행한다 — 뚜껑이 닫히면 디스플레이/윈도우 서버가 비활성화돼 이후 모든 GUI 자동화 단계가 각자 타임아웃되며 조용히 실패해 원인 파악이 어려웠다(8절) | 필수 |
| FR-14 | 모든 대상 방 처리가 끝난 뒤 방별 성공/실패를 요약해 로그로 남긴다. 하나라도 실패하면(부분 실패 포함) 종료 코드를 0이 아닌 값으로 반환한다 | 필수 |
| FR-15 | 메시지 원문 전체는 로그에 남기지 않는다 — 방 이름, 메시지 길이, 성공/실패 여부만 기록한다(개인 대화 내용이 로그 파일에 평문으로 남는 것을 방지하기 위한 설계 판단) | 필수 |
| FR-16 | System Events 호출이 손쉬운 사용(Accessibility) 권한 거부로 실패하면, 재시도 없이 명확한 에러 메시지(권한 부여 방법 안내 포함)와 함께 완전 실패로 처리한다. `cliclick` 자체도 동일한 권한 범주의 영향을 받을 수 있어 함께 안내한다 | 필수 |
| FR-19 | 실행 로그를 `data/kakaotalk_sender.log`(회전, 최대 2MB × 3개)에도 항상 남긴다 — 이 스킬은 `ai_news_telegram`에서 best-effort로 서브프로세스 호출되는데, 방 일부만 실패해도 호출한 쪽은 exit 0으로 끝나 Hermes 크론이 stderr를 통째로 버리는 바람에 2026-08-16/17 두 차례 사고 모두 시스템 로그(`log show`)로 정황만 재구성해야 했다(8절). 종료 코드와 무관하게 항상 남는 파일 로그로 다음부터는 원인을 바로 확인할 수 있게 한다. FR-15(메시지 원문 미기록)는 이 파일 로그에도 동일하게 적용된다 | 필수 |

## 4. 비기능 요구사항
- **성능**: 방 개수만큼 순차 처리하며, UI 반응 대기가 포함돼 방 1개당 수 초가 소요된다
  (Phase 0 실측: 검색~전송 검증까지 방 1개당 약 5~8초). 전체 처리 시간에 대한 상한은
  두지 않는다.
- **신뢰성**: 자동 재시도를 두지 않는다(FR-13). 대신 두 단계 검증(FR-10 붙여넣기 확인,
  FR-12 전송 검증)으로 "실패했는데 성공으로 오인하는" 상황을 최소화한다. Phase 0에서
  실제로 "입력창은 비워졌지만 메시지가 도착하지 않은" 오탐 사례가 여러 차례 재현되어,
  입력창 상태만으로는 성공을 판단할 수 없다는 것이 실증됐다(FR-11, FR-12).
- **안전성(오동작 방지)**: Phase 0에서 두 가지 실제 오동작이 재현됐다 — (1) 오래된 화면
  좌표를 재사용해 더블클릭한 결과 의도한 방이 아닌 다른 실제 대화방이 열린 사례, (2)
  frontmost 확인 없이 진행하다 키 입력이 KakaoTalk이 아닌 다른 앱(VS Code)으로 전달된
  사례. 이 경험을 바탕으로 FR-5(frontmost 안전장치)와 FR-7의 방 이름 재확인을 필수
  요구사항으로 격상했다. 좌표는 매 상호작용 직전 새로 조회하며 캐시하지 않는다(창 위치가
  호출 사이에 이동할 수 있음이 확인됨).
- **보안**: 별도로 저장하거나 다루는 자격 증명이 없다(기존 로그인 세션을 그대로
  사용하므로 비밀번호/토큰/세션 값을 코드가 직접 다루지 않는다). 메시지 원문은
  로그에 남기지 않는다(FR-15).
- **로깅/모니터링**: 표준 `logging` 모듈로 앱 활성화 결과, 방별 검색/열기/붙여넣기 확인/
  전송/전송 검증 결과, 최종 요약을 기록해 Hermes가 실행 로그로 성공/부분 실패/완전 실패를
  판단할 수 있게 한다. `print`는 사용하지 않는다(`CLAUDE.md` 3.4).
- **플랫폼 제약**: macOS 전용. KakaoTalk 데스크톱 앱이 설치되어 있고 이미 로그인된
  상태여야 하며, 화면 잠금이 해제된 상태에서 실행해야 한다(Phase 0에서 미검증 —
  Implementation Plan 4절 참고). 실행 프로세스(터미널 등)에 손쉬운 사용(Accessibility)
  권한이 부여되어 있어야 하며, `cliclick`(Homebrew)이 설치되어 있어야 한다.

## 5. 입출력 명세
### 5.1 입력
| 항목 | 타입 | 필수 여부 | 유효성 규칙 | 설명 |
|---|---|---|---|---|
| `--room` | 커맨드라인 인자(반복 가능) | 필수(최소 1개) | 빈 문자열 불가 | 메시지를 보낼 대화방 이름(정확히 일치) |
| `--message` | 커맨드라인 인자 | `--message-file`과 상호배타, 둘 중 하나 필수 | 빈 문자열 불가 | 전송할 메시지 본문 |
| `--message-file` | 커맨드라인 인자(파일 경로) | `--message`와 상호배타, 둘 중 하나 필수 | 파일이 존재하고 읽기 가능해야 함 | 전송할 메시지 본문을 담은 텍스트 파일(긴 리포트 등) |

### 5.2 출력
| 항목 | 타입 | 설명 |
|---|---|---|
| 실행 로그 | 로그(표준출력/로그 파일) | 앱 활성화 결과, 방별 성공/실패, 실패 사유(방 못 찾음/붙여넣기 확인 실패/전송 검증 실패/frontmost 불일치/권한 없음 등) |
| 종료 코드 | 정수 | 전체 성공 시 0, 완전 실패 또는 부분 실패 시 0이 아닌 값 |

DB 등 상태 저장은 하지 않는다(무상태 실행). 다만 진단을 위한 실행 로그 파일
(`data/kakaotalk_sender.log`)은 예외적으로 남긴다(FR-19, 2026-08-17 추가 — 회전 로그라
무한정 누적되지 않는다).

## 8. 외부 의존성
- **외부 API/서비스**: 없음. 카카오톡 공식/비공식 API, LOCO 프로토콜, 세션 토큰 추출 등을
  전혀 사용하지 않는다 — 이미 로그인되어 실행 중인 데스크톱 앱을 UI 자동화로 조작하는
  방식만 사용한다. (이 설계는 "agent-messenger" 등 세션 토큰을 추출하는 서드파티 패키지의
  계정 정지·공급망 리스크를 피하기 위해 의도적으로 선택했다.)
- **대안 재검토(2026-08-15, 무인 실행 문제로 GUI 자동화 자체를 재검토하며 조사)**: 뚜껑
  닫힘/화면 절전 문제가 드러난 뒤, GUI 자동화를 LOCO 프로토콜 기반 라이브러리로
  대체하는 방안을 다시 조사했다. 결과: (1) Python용 LOCO 라이브러리는 전부 2013~2020년에
  멈춘 죽은 프로젝트로 현재 카카오 서버와 호환되지 않는다. (2) `node-kakao`는 2026년
  현재 npm에서 "더 이상 지원 안 함"으로 표시되어 있고, 이를 살리려던 커뮤니티 포크
  (`antegral/kakao-nibs`)도 2026년 6월 "현재 작동 안 함"으로 아카이브됐다 — 프로토콜/버전
  불일치로 인한 영구 정지 사례도 보고되어(GitHub Discussion #616) 오히려 GUI 자동화보다
  계정 리스크가 크다. (3) 카카오 공식 API는 2026년 5월 카카오 담당자가 재확인한 대로
  개인 단체방 발송 기능을 제공하지 않는다(채널/오픈채팅봇만 가능). 결론: 대안이 전부 더
  나쁜 상태라 GUI 자동화를 유지하고, 근본 원인(디스플레이 절전)을 운영 환경(외부 모니터
  +`caffeinate`, 10절)으로 해결하는 쪽을 택했다.
- **인증 방식 및 필요한 자격 증명**: 없음. 기존 로그인 세션을 그대로 재사용하므로 비밀번호,
  토큰, API 키 등을 다루지 않는다. `.env`/`docs/ENVIRONMENT.md`에 추가할 항목 없음.
- **시스템 의존성 (Phase 0에서 확정, 당초 예상과 다름)**: **`cliclick`**(Homebrew 패키지,
  `brew install cliclick`)이 필수다. macOS 접근성 API의 합성 클릭(`System Events`의
  `click`/`perform action "AXPress"`)과 일부 합성 키 입력(`keystroke ... using {command
  down}`)이 이 카카오톡 Mac 앱의 커스텀 렌더링 UI 요소(채팅방 목록/검색 결과 행, 전송
  버튼, 클립보드 붙여넣기)에서 간헐적으로 또는 전혀 반응하지 않음이 Phase 0 스파이크에서
  실증됐다. `cliclick`은 실제 HID 이벤트에 가까운 합성 이벤트를 생성해 이 문제를
  우회한다. Homebrew 자체가 설치되어 있지 않은 환경에서는 Homebrew 설치가 선행되어야
  한다(README에 안내 예정).
- **Python 패키지**: 표준 라이브러리만 사용(`argparse`, `logging`, `subprocess`,
  `platform`, `shutil`). 별도 pip 패키지는 필요하지 않다 — 당초 검토했던 `pyobjc-framework
  -Quartz` 경로는 `cliclick` 도입으로 불필요해졌다.
- **macOS 요구사항**: 손쉬운 사용(Accessibility) 권한을 실행 프로세스(터미널 또는
  Hermes 실행 환경)에 부여해야 한다. `cliclick`도 동일한 권한 범주의 영향을 받을 수
  있다. KakaoTalk 데스크톱 앱 설치 및 로그인 필요.
- **Phase 0 실사 확인 결과 요약**:
  - 채팅방 목록/검색 결과는 `AXTable`의 row로 접근 가능하며, 각 row의 `AXCell` 하위
    `AXStaticText` 값으로 방 이름을 정확히 매칭할 수 있다.
  - 방을 여는 것은 `cliclick`의 더블클릭(`dc:x,y`)으로만 안정적으로 동작한다. System
    Events의 `click`/`AXPress`로는 열리지 않는다.
  - 검색창 포커스는 `cliclick`의 단일 클릭(`c:x,y`)이 필요하다(그냥 `click` 명령으로는
    포커스가 붙지 않아 이후 타이핑이 무시됨). 포커스가 붙은 뒤의 텍스트 입력 자체는
    System Events `keystroke`로 정상 동작한다.
  - 메시지 입력창(`AXTextArea`, description "메시지 입력")도 `cliclick` 단일 클릭으로
    포커스해야 한다.
  - 클립보드 붙여넣기는 `cliclick`의 `kd:cmd t:v ku:cmd` 조합으로 안정적으로 동작한다.
    System Events의 `keystroke "v" using {command down}`은 포커스가 정확히 확인된
    상태에서도 간헐적으로 무시되는 사례가 반복 재현되어 채택하지 않는다.
  - 입력창의 접근성 `value` 속성은 실제 내용이 있어도 빈 값으로 보고되는 등 신뢰할 수
    없다. 대신 전체선택(`Cmd+A`)+복사(`Cmd+C`) 후 시스템 클립보드를 다시 읽는 방식으로
    실제 내용을 확인할 수 있다.
  - 멀티라인 텍스트(줄바꿈 포함)는 클립보드 붙여넣기로 정상 전달되며, 줄바꿈이 그대로
    유지된 채 전송·표시된다(실제 발송으로 확인).

  어떤 에러 메시지로 실패했는지)가 남아있지 않아 — best-effort 호출자가 exit 0으로
  끝나면 Hermes 크론이 stderr를 버리는 동일한 문제(위 2026-08-16 항목과 같은 구조)
  — 시스템 로그 정황만으로 재구성한 추정이다. 같은 문제가 반복되지 않도록 exit
  코드와 무관하게 항상 남는 파일 로그(FR-19)를 함께 추가했다.

## 9. 테스트 시나리오
| 시나리오 | 입력 | 기대 결과 |
|---|---|---|
| 정상 케이스(단일 방) | `--room "테스트방" --message "안녕"`, 앱 정상/로그인됨 | 검색→방 열기(이름 재확인)→붙여넣기(확인)→전송→전송 검증까지 성공, 종료 코드 0 |
| 정상 케이스(여러 방) | `--room "방A" --room "방B" --message "..."` | 두 방 모두 순차 전송 성공, 종료 코드 0 |
| `--message-file`로 긴 리포트 전송 | `--message-file report.txt`(멀티라인) | 줄바꿈 포함 그대로 전송, 종료 코드 0 |
| 인자 오류(둘 다 없음) | `--room "방A"`만 지정 | 실행 시작 전 종료, 에러 로그, 종료 코드 0이 아님 |
| 인자 오류(둘 다 지정) | `--message "a" --message-file f.txt` 동시 지정 | 실행 시작 전 종료, 에러 로그, 종료 코드 0이 아님 |
| `cliclick` 미설치 | PATH에 `cliclick` 없음 | 실행 시작 전 종료, 설치 안내 에러 로그, 종료 코드 0이 아님 |
| 존재하지 않는 방 | `--room "없는방"` | 해당 방 실패로 기록, 종료 코드 0이 아님 |
| 방 이름 중복 | 동일 이름의 채팅방/검색 결과가 2개 이상 | 해당 방 실패로 기록(임의 선택 없음), 종료 코드 0이 아님 |
| 방 열기 후 이름 불일치(misfire) | 더블클릭 후 열린 창 이름이 대상과 다름 | 해당 방 즉시 실패로 기록, 다른 실제 대화방에 메시지 전송 시도하지 않음, 종료 코드 0이 아님 |
| 붙여넣기 확인 실패 | 클립보드 재확인 결과가 원본과 불일치 | 전송 시도 안 함, 해당 방 실패로 기록, 종료 코드 0이 아님 |
| 전송 검증 실패 | 전송 버튼 클릭 후 대화 내역에 텍스트 미확인 | 해당 방 실패로 기록, 종료 코드 0이 아님 |
| 방 창 정리 후 남은 창 발견 | `close_all_room_windows()` 실행 후 메인 목록 창 외 창이 남음(예: 정리 AppleScript 타임아웃) | `CLOSE_WINDOWS_MAX_ATTEMPTS`까지 재시도, 그래도 남으면 에러 로그(FR-17) |
| 부분 실패 | `--room "방A" --room "없는방"` | 방A는 성공, "없는방"은 실패로 요약 로그에 표시, 종료 코드 0이 아님 |
| 앱 로그인 안 됨 | KakaoTalk.app이 로그인 화면 상태 | 완전 실패, 어떤 방도 시도하지 않음, 종료 코드 0이 아님 |
| Accessibility 권한 없음 | 손쉬운 사용 권한 미부여 상태에서 실행 | 완전 실패, 권한 안내 에러 로그, 종료 코드 0이 아님 |
| frontmost 불일치 | 상호작용 직전 다른 앱이 최상단 | 그 시점 방은 즉시 실패로 기록, 종료 코드 0이 아님 |

실제 UI 자동화(cliclick/System Events ↔ KakaoTalk.app) 부분은 macOS 환경과 로그인된
카카오톡 계정, 실제 테스트용 대화방이 있어야 검증 가능하므로, 외부 호출(`subprocess`)을
mock 처리한 스모크 테스트를 기본으로 하고(인자 검증, 방별 결과 집계/종료 코드 결정 로직
등), 실제 전송 확인은 Phase 0에서 이미 수동으로 1차 검증했으며 이후 Phase에서도 수동
실행으로 재확인한다(`CLAUDE.md` 3.5).

## 10. 제약사항 / 비범위
- **[운영상 필수 조건] 예약 실행 시점에 디스플레이가 절전/화면 잠금에 들어가 있지
  않아야 한다 — 두 가지 독립된 원인을 모두 해결해야 한다(8절, 2026-08-14~15 사고로
  확인).** 이는 `kakaotalk_sender` 코드만으로 전부 해결할 수 있는 문제가 아니라 macOS
  자체의 전원 관리 동작이다. FR-18은 뚜껑이 닫힌 상태를(2026-08-16부터는 외부 모니터
  연결로 실제 잠들지 않는 클램쉘 모드까지 구분해) 조기 감지하지만, 유휴 시간으로 인한
  디스플레이 절전/화면 잠금은 별도 원인이라 FR-18로 감지되지 않고 이후 단계에서
  타임아웃으로 나타난다.
  1. **뚜껑이 닫혀 있으면 안 된다 — 단, 외부 모니터가 연결되어 있으면 예외.** 외부
     모니터(또는 HDMI 더미 플러그) 없이 뚜껑이 닫히면 하드웨어 레벨에서 디스플레이가
     강제로 꺼진다. 뚜껑을 닫아야 한다면 반드시 외부 모니터/더미 플러그를 연결하고
     전원 어댑터를 꽂아둬야 한다(클램쉘 모드). 이 예외 상태는 FR-18이 `ioreg`의
     `AppleClamshellCausesSleep` 값으로 자동 판별한다(2026-08-16 이전에는 이 판별이
     코드에 빠져 있어 외부 모니터를 연결해도 조기 실패했다 — 8절 2026-08-16 항목 참고).
  2. **유휴 시간에 따른 디스플레이 절전/화면 잠금도 막아야 한다 — 뚜껑이 열려 있어도,
     외부 모니터가 연결돼 있어도 마찬가지로 적용된다.** 이 Mac은 유휴 10분 후 디스플레이
     절전, 그로부터 5분 뒤(`sysadminctl -screenLock status`) 화면 잠금(암호 요구)이
     걸리도록 설정되어 있었다. 새벽 예약 실행 시점은 마지막 조작 후 몇 시간이 지난
     뒤라 이미 화면 잠금까지 걸려 있을 수밖에 없고, **한 번 화면 잠금이 걸리면 실행
     직전에 "깨우는" 명령으로는 풀 수 없다**(암호를 자동 입력할 수 없으므로) — 실제로
     `caffeinate -u`로 디스플레이만 깨운 상태에서는 방 열기·붙여넣기·전송까지는
     성공했지만 `caffeinate` 유지 시간이 짧으면 도중에 다시 잠들어 마지막 검증
     단계에서 실패하는 것까지 실측으로 확인했다. 따라서 단발성 wake가 아니라 **로그인
     세션 동안 상시** `caffeinate -d -i -s -u`(디스플레이/유휴/시스템 절전 방지 + 사용자
     활성 상태 유지)를 실행해두는 launchd LaunchAgent(`~/Library/LaunchAgents/
     com.devjan.keepawake.plist`, 이 저장소 밖의 머신 설정)로 해결했다.
  두 조건이 모두 충족돼야(외부 모니터+전원 연결, keepawake LaunchAgent 실행 중) 새벽
  무인 실행에서도 실제 배송이 된다.
- macOS 전용이며 Windows/Linux는 지원하지 않는다.
- 텍스트 메시지 전송만 지원한다. 이미지/파일/이모티콘 전송은 이번 버전 범위 밖이다.
- 메시지 수신/대화 내역 읽기 기능은 없다(발신 전용 — 단, 전송 검증을 위해 최근 대화
  내역을 읽는 내부 로직은 있다).
- 대화방 생성, 초대 등 채팅방 관리 기능은 없다. 이미 존재하는 대화방에만 보낼 수 있다.
- 자동 로그인/최초 인증 자동화는 하지 않는다. 로그인이 안 되어 있으면 완전 실패로
  처리하고, 사용자가 직접 로그인한 뒤 재실행해야 한다.
- 자동 재시도를 두지 않는다(4절, FR-13).
- **`cliclick`(Homebrew) 설치가 전제 조건이다** — 당초(2026-08-10 초안) "표준 라이브러리로
  충분할 것"이라 예상했으나, Phase 0 실사 확인 결과 이 앱의 UI 자동화에는 필수임이
  확인되어 이 SRS를 갱신했다(8절).
- 화면 잠금 상태에서의 정확한 실패 형태(에러 메시지/코드)는 Phase 0/Phase 2 모두에서
  실제로 재현해 확인하지 않았다 — 화면을 실제로 잠가야 재현 가능해 검증을 보류했다
  (Implementation Plan Phase 2 참고). 현재 코드는 이 상태를 별도로 분류하지 않으며,
  `KakaoTalkNotLoggedInError` 또는 일반 예외로 처리될 것으로 추정만 하고 있다.
- **전송 검증(FR-12)이 긴 메시지에서 신뢰할 수 없다(알려진 문제, 미해결)**: 실제 AI
  뉴스 리포트 수준의 텍스트(약 1,800자, 여러 항목·링크 포함)를 "금칠"/"화공97"/
  "고대97" 3개 방에 실사용으로 보낸 결과, **전송 자체는 매번 성공**했지만(사용자가
  직접 확인) **전송 검증 단계는 타임아웃(35초로 상향한 뒤에도)으로 매번 실패**했다.
  즉 현재 버전은 이 정도 길이의 메시지에서 `kakaotalk_sender`가 "실패"를 보고해도
  실제로는 도착했을 가능성이 높다 — 로그/종료 코드만으로는 실제 성공 여부를 신뢰할 수
  없는 상태다. 원인으로는 (1) 긴 문자열 비교 자체가 접근성 API를 통해 느리다는 점,
  (2) 카카오톡이 대화 내역의 접근성 값을 어느 길이 이상에서 말줄임(…)으로 잘라
  노출해(실제로 493자에서 잘린 사례 확인) 애초에 정확 일치가 성립하지 않을 수 있다는
  점 두 가지를 의심하고 있으나 근본 원인은 확정하지 못했다. 검증 로직을 길이에 따라
  분기하거나(예: prefix 일치, 또는 아예 다른 신호 사용) 재설계하는 것을 다음 패치에서
  검토해야 한다.
- 메시지 최대 길이의 정확한 상한은 확정하지 않는다. 다만 위와 같이 약 1,800자 수준의
  텍스트도 전송 자체(붙여넣기+전송)는 성공한다는 것은 확인했다. 이보다 훨씬 긴 텍스트나
  분할 전송 정책은 필요해지면 추가 버전에서
  다룬다.
